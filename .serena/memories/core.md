# branch_bench — core

Single-file C99 microbenchmark measuring branch-misprediction cost. `AGENTS.md` (pulled in by `CLAUDE.md`) is the authoritative human-written guide: test descriptions, kernel conventions, perf timing window rules. Don't duplicate it; consult it first.

## Source map
- `branch_bench.c` — everything. Section order: perf_event support (`#ifdef HAVE_PERF`) → tunables (`ARRAY_LEN`, `REPS`, `THRESHOLD`, `NUM_FUNCS`, `DISPATCH_N`) → timing/PRNG → report helpers (`get_cpu_model`, `ReportRow`, `report_table`) → `run_test1..4` with their kernels → `INTERP_GUIDE` → `main`.
- `run.sh` — canonical build+run.
- `RESULTS.md` — collected per-CPU reports, one `## <CPU>` section each (generated by `-o`, then appended by hand).
- `README.md` — short user-facing notes.
- Build output `branch_bench` is gitignored.

## Invariants / gotchas
- Must stay a single self-contained `.c` file with no deps beyond libc and Linux headers.
- Platform split: `HAVE_PERF` is defined only on Linux when `__NR_perf_event_open` exists. On AArch64/ARM, `perf_init` falls back to raw PMU events (0x12 BR_PRED, 0x21 BR_MIS_PRED) for cores where the generic events fail (e.g. Pi 4 / Cortex-A72). Every perf use must compile away cleanly without `HAVE_PERF`.
- `get_cpu_model` parses `/proc/cpuinfo` (`model name` on x86, `Model`/`Hardware` on ARM). In `RESULTS.md`, the clock speed and suffixes like `(WSL2)` / board names in headings were added by hand, not emitted by the program.
- The interpretation guide exists twice: the `printf` block in `main` and the `INTERP_GUIDE` string used for the report. Edit both together.
- Console output and the Markdown report are written in parallel in each `run_testN`. A change to one usually needs the matching change to the other (`report == NULL` when `-o` isn't given).
- The comment on `ARRAY_LEN` says "1 048 576" but the value is `1u << 22` (4 194 304); trust the value.
